# mbedTLS 3.6.8 advisories: which reach the display, and which core fixes them (ticket 43), 26 Nov 2026

Question: the display runs arduino-esp32 core 3.3.13 with mbedTLS 3.6.7. mbedTLS 3.6.8 (16 Nov 2026) lists 21 security advisories. Which of them can be reached on this display (TLS client only, TLS 1.2, TLS 1.3 off, renegotiation compiled in, built-in certificate bundle), and which arduino-esp32 release first ships a fixed mbedTLS? Feeds ticket 51 ("move to the core that fixes mbedTLS").

Everything below was read from files and web pages on 26 Nov 2026. Nothing was flashed, no serial port was opened, nothing under `~/Library/Arduino15` was modified (the core 4.0.0 files were downloaded into a scratch folder and only read).

## Answer in five lines

1. **None of the 21 can be reached on the display as it is built today**: 0 reachable, 0 unknown, 21 not reachable. By reason: 5 are TLS 1.3 code that is not compiled in (1-5); 3 more are server-side bugs and the display never runs a TLS server (9, 17, 18); 8 need a feature that is not in the firmware image (CRLs 6 and 8, PSA ECJPAKE 7, p256-m 10, software AES 12, PSA ECC 15, the variable-buffer option 16, `mbedtls_x509_dn_gets` 20); 3 need a local or physical attacker (13, 14, 21); 2 need an input the firmware never gives the library (an encrypted private key 11, a URI as the expected name 19).
2. The two the current docs call out do not apply: the renegotiation use-after-free (CVE-2026-93844) needs `MBEDTLS_SSL_VARIABLE_BUFFER_LENGTH`, which is **off** (`# CONFIG_MBEDTLS_SSL_VARIABLE_BUFFER_LENGTH is not set`), and the core never switches renegotiation on at run time; the Subject Alternative Name bug (CVE-2026-90470) needs a URI as the expected name, and the saved service host can only hold letters, digits, `.` and `-`.
3. **No arduino-esp32 release carries the fix yet.** 3.3.13 (17 Nov) has mbedTLS 3.6.7; there is no 3.3.14 (checked 26 Nov). 4.0.0 (19 Nov) is built on ESP-IDF v6.1.1 and has mbedTLS **4.1.1**, which the advisories also list as affected (fixed in 4.1.2). ESP-IDF `release/v5.5` (v5.5.6 and the branch head) still points at 3.6.7. Espressif's fork already has branches `mbedtls-3.6.8-idf` (17 Nov) and `mbedtls-4.1.2-idf` (18 Nov), but no ESP-IDF branch or release points at them yet.
4. Two of the 21 have **no fixed version anywhere** (CRL name matching, AES ROM tables): the project's advisory pages give only a workaround, and neither applies here.
5. **Ticket 51 is not doable now.** Stay on 3.3.13, do not jump to 4.0.0 (it is not fixed and is a major migration), and redo ticket 51 as a patch bump when the first 3.3.x core whose libs report mbedTLS 3.6.8 or later appears (how to detect it is in the recommendation).

## How reachability was decided

- **Compiled in?** The core's `sdkconfig` (`~/Library/Arduino15/packages/esp32/tools/esp32s3-libs/3.3.13/sdkconfig`) and the effective mbedTLS configuration headers (`include/mbedtls/port/include/mbedtls/esp_config.h`, `include/mbedtls/mbedtls/include/mbedtls/mbedtls_config.h`) in the same folder. The library is Espressif's copy, version string `3.6.7` in `build_info.h`.
- **In the firmware image?** The pre-built libs hold much more than the sketch links. I read the symbol table of the firmware ELF built from this repo for core 3.3.13 (`xtensa-esp32s3-elf-nm`) and the linker's cross-reference table, so "not in the image" below means the function is not in the program that runs on the board. The ELF is from the lead's build of 25 Nov (flash 1.48 MB); the TLS-related code did not change since.
- **Reachable by the display's code paths?** `arduino/ledmatrix/live.cpp` (`connectDual`: `NetworkClientSecure`, `useBuiltinCACertBundle()`, `connect(ip, 443, host, nullptr, nullptr, nullptr)` so no client certificate, key, or pre-shared key), the core's `libraries/NetworkClientSecure/src/ssl_client.cpp`, and `settings.cpp` / `deviceauth.h` (`lowerHost`) for what a host name can contain.
- **What an attacker can do.** The display talks TLS 1.2 as a client to one saved service host (and `api6.ipify.org` / `api64.ipify.org` in the self-test). A malicious server or someone on the network path who holds a certificate that chains to the built-in bundle for that name (or a changed saved host) can send any TLS 1.2 handshake message. The library paths that such a peer drives are ServerHello, Certificate (X.509 parsing and name check), ServerKeyExchange (ECDHE), CertificateRequest, NewSessionTicket (kept as opaque bytes) and alerts. None of the 21 advisories is in those paths in this build, apart from the name check (advisory 19), which is not triggered by a host name.
- **Wi-Fi.** `CONFIG_ESP_WIFI_MBEDTLS_TLS_CLIENT=y` and `CONFIG_WPA_MBEDTLS_CRYPTO=y` are on, but they matter for WPA2-Enterprise (EAP-TLS) and WPA3-SAE's elliptic-curve maths. The display joins with a pre-shared Wi-Fi password, so the wpa_supplicant TLS client is not used; SAE uses raw curve arithmetic that none of the 21 advisories names (apart from the local-attacker ones).
- **What I could not check.** Whether Espressif has said anything about transient-execution (Spectre) attacks on the ESP32-S3: I found no statement, so the four Spectre rows rest on "needs a local attacker" alone. The `.elf` I inspected is a recent build, not the exact binary on the board.

Upstream releases: Mbed TLS 3.6.8, 4.1.2 and 4.3.0 were all published on 16 Nov 2026 (GitHub releases). Core libs are rebuilt by Espressif's `esp32-arduino-lib-builder` from an ESP-IDF branch, and arduino-esp32 publishes them in the next release (the pull requests titled "IDF release/v5.5", for example 13112, merged 17 Nov, carry them; the 3.3.13 libs report ESP-IDF `a45de8cc`). The open PR 13165 "IDF release/v6.1" (24 Nov) is built on `release/v6.1` at `c43d665a`, whose mbedTLS submodule is still 4.1.1 (4.0.x is therefore not about to be fixed by it). There is no announced date for an ESP-IDF update to 3.6.8; I found no issue or pull request in `espressif/esp-idf` or `espressif/arduino-esp32` that mentions mbedTLS 3.6.8 or any of the 21 CVEs (searched 26 Nov).

So, plainly: **no 3.3.x release carries the fix yet, and no 4.x release does either.** The fix will reach the display in the first arduino-esp32 release built on an ESP-IDF branch that has taken `mbedtls-3.6.8-idf` (for the 3.3.x line, an ESP-IDF 5.5 update) or later.

A longer-term point from the same sources: the 3.6 line is supported by Mbed TLS until 28 Mar 2027 (3.6.8 release notes), and the Mbed TLS maintainers said on 8 Oct 2026 that they would stop maintaining the TLS and X.509 libraries from April 2027 unless new maintainers join (quoted in ESP-IDF issue 19229, closed 28 Oct with "we will have more visibility by Q2 next year"). That affects how long a 3.3.x core, whose TLS is mbedTLS 3.6, will keep receiving TLS fixes.

## Recommendation for ticket 51 ("move to the core that fixes mbedTLS")

**Not doable now.** No released core has the fix, so there is nothing to move to. Keep 3.3.13 and keep ticket 51 blocked on a trigger.

- **Exposure while waiting: none known.** None of the 21 is reachable on the display (table above), and no code or setting change is needed. The reachability results hold only while the core's configuration stays as it is: re-check them if a future core turns TLS 1.3 on, turns on `CONFIG_MBEDTLS_SSL_VARIABLE_BUFFER_LENGTH`, or enables the p256-m driver.
- **Do not move to 4.0.0 for this reason.** It is not fixed (mbedTLS 4.1.1), it is seven days old, and it is a major migration: ESP-IDF 6.1, mbedTLS 4 with PSA crypto, a different compiler (GCC 15.1, C23 for `.c` files). By my inference (mbedTLS 4 routes all crypto through PSA, and the 4.0.0 libs list `CONFIG_MBEDTLS_KEY_EXCHANGE_ECJPAKE=y`; I did not inspect the 4.0.0 image) it would also put PSA code (`psa_*`) in the image, where today there is none, so the PSA advisories (7 and 15) would stop being "not compiled in"; they would still need a local attacker or an oversized-buffer condition, but it is a worse starting point, not a better one. The core's own 3.x to 4.0 guide says: NetworkClientSecure "now runs on Mbed TLS 4.0 (PSA Crypto)", finite-field DHE and non-forward-secret `TLS_RSA_*` suites are removed, curves under 250 bits are unsupported, legacy `mbedtls_*` crypto APIs were removed, `HTTPClient` no longer skips certificate verification by default (the firmware does not use `HTTPClient`). A first-hand compile of the firmware on 4.0.0 was not done (it needs a second toolchain install; not tested here).
- **What the first fixed 3.3.x will be.** A patch bump within the same ESP-IDF 5.5 line, the lowest-risk kind of change. Known compatibility between 3.3.13 and 4.0.0, for the day a fixed 4.0.x exists (read from 4.0.0's files, not run):
  - `boards.txt` entry `adafruit_matrixportal_esp32s3`: identical except the Zigbee library names in the Zigbee-mode menu; same vendor/product ids, same TinyUF2 partition schemes (`tinyuf2` with `upload.extra_flags=0x410000 .../variants/adafruit_matrixportal_esp32s3/tinyuf2.bin`, `build.custom_bootloader=bootloader-tinyuf2`); the variant folder (including `tinyuf2.bin` and the TinyUF2 bootloader) is byte-identical; `tools/partitions/tinyuf2-partitions-8MB.csv` identical. The project's own `partitions.csv` still wins because it sits in the sketch folder.
  - `NetworkClientSecure`: `setHandshakeTimeout` still multiplies by 1000, so the unit is still seconds (the same as the comment in `live.cpp`); the 6-argument `connect(ip, port, host, ...)` form used by `connectDual` is unchanged; `useBuiltinCACertBundle()` is unchanged (`NetworkClientSecure.h` differs only in one comment). `ssl_client.cpp` already carries `#if MBEDTLS_VERSION_MAJOR >= 4` branches in 3.3.13, so the core is prepared for mbedTLS 4.
  - `esp_efuse` / `esp_hmac`: every function the firmware calls (`esp_efuse_get_key_purpose`, `esp_efuse_key_block_unused`, `esp_efuse_get_key_dis_read/write`, `esp_efuse_get_keypurpose_dis_write`, `esp_hmac_calculate`, `esp_efuse_mac_get_default`) is declared in the 4.0.0 libs' headers. `mbedtls/md.h` is still shipped with `mbedtls_md_setup/starts/update/finish/hmac`, which `ota.cpp` and `signers.h` use.
  - `Preferences`, `esp_ota_ops.h`: no change listed in the migration guide or release notes (not compiled).
  - `WebServer`: the migration guide lists new request limits (408, 414, 431 responses), SSE moved to `enableSSE()`, digest auth changes, `serveStatic()` rejecting dot segments. The portal's multipart firmware upload and its form posts need a re-test.
  - Adafruit Protomatter 1.7.1 (the pinned version) was last reported tested on 3.3.11 and 4.0.0-alpha1 (`wayfinder/research/firmware-options.md`); its repository has IDF 6 related commits from Oct 2026 but no release after 1.7.1 (5 Sep 2025). The frame-gap test is the one that would show a regression.
- **How to know the fixed core has arrived** (check monthly, as `docs/security.md` already asks, or when an advisory appears):
  1. A new arduino-esp32 3.3.x release (14, 15, ...) on the releases page, and in its notes an "IDF release/v5.5" line.
  2. Confirm without installing: `gh api 'repos/espressif/esp-idf/contents/components/mbedtls/mbedtls?ref=release/v5.5' --jq .sha` no longer prints `2b96dd8eebe880f304c69976b3c2fa0c5100cbb6` (the 3.6.7 head), and the new value is the head of `mbedtls-3.6.8-idf` (`63df813d` on 17 Nov) or later.
  3. After `arduino-cli core install esp32:esp32@<version>`, `grep MBEDTLS_VERSION_STRING ~/Library/Arduino15/packages/esp32/tools/esp32s3-libs/<version>/include/mbedtls/mbedtls/include/mbedtls/build_info.h` prints `"3.6.8"` (or later 3.6.x), and the `sdkconfig` in the same folder still has `# CONFIG_MBEDTLS_SSL_PROTO_TLS1_3 is not set` and `# CONFIG_MBEDTLS_SSL_VARIABLE_BUFFER_LENGTH is not set`.
- **When it arrives, ticket 51's checklist stands as written**: pin the version in `.github/workflows/service.yml` (`ESP32_CORE_VERSION`) and in the docs (`build.md`, `development.md`, `security.md`, `operations.md`, README line 112), check the four pinned libraries still resolve, compile and run every host test and the margin check, then the bench tests (update through the real path, rollback, revoked-key update, frame gaps), then release.
